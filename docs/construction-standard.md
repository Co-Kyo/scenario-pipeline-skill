# sp-skill-dev 施工标准：开发心智负担

> 定位：本仓内部施工标准，回答"什么样的项目结构算优雅"。
> 它不是测试，不进 `npm test`，没有红绿；它是**怎么做才是好代码、好项目的过程标准**。
> 存放：`docs/construction-standard.md`（本文件）＋ `docs/reading-trees/`（逐步阅读树样板）。
> 与 slides／deck／STORY 无关：那些是过程记录，这是施工依据。

## 一、为什么需要这套标准

本仓的工作重心已经转到拆包、package 标准化、过程优化上。此前我们一直在原子上动手脚（形状对不对、边界清不清），但从来没有从工程角度完整回答过：

> 一个完全不知道 sp-skill 是什么的开发者，读完本仓代码要付出多少心智负担？

如果这个问题没有量化答案，所有"正确"都是空中楼阁——为了正确而正确。

## 二、理论：把开发者的大脑看成训练流程的一环

Skill 产物最终喂给 agent，但**开发者的大脑是更早的一环**：项目的复杂度必须先装进人的脑子，才能被正确地改、拆、发包。

所以这套标准衡量的不是文件本身，而是**复杂度在大脑中 pre-fill 的效率**：

- 对新人：从零到"敢改一步"要开几个文件、记几个新概念、跳几层目录。
- 对自己人：改一处时心里要装几处（改这里要看哪里），管项目时的常驻心智负担有多大。

阅读树就是 pre-fill 的路线图：树画得出来，负担就看得见；树画不出来，说明结构本身已经装不进脑子了。

## 三、树画什么：新人阅读树

不是文件罗列。每个节点回答四个问题：

| 节点四问 | 含义 |
|---|---|
| 这是什么文件 | 路径 |
| 多大 | 行数（实测） |
| 教几个新东西 | 新概念数（只数本文件首次出现的概念） |
| 跳到哪去 | 跳转数（import＋注册表路径＋引用） |

分层固定四层，从外往里读（pre-fill 顺序）：

```
产物层（dist 某步 md：先知道长什么样）
  → 装配层（steps/index、contracts、modules、entities：谁跟谁接线）
    → 单步层（steps/某步＋domain/content/某域＋assets/某目录：做法与声明）
      → 内容包层（src/packages/某包 blocks：通用形状）
```

每个节点标"先读"顺序号。新人按号走，每一步的工作集（同时打开的文件）有界，即为合格的树。

## 四、负担五数（只记录，不设红）

| 数 | 定义 | 怎么数 |
|---|---|---|
| 阅读步数 | 读懂一步要开几个不同文件 | 数树节点数 |
| 单步三处总行数 | steps/某步＋domain/content/某域＋assets/某目录行数之和 | `wc -l` 相加 |
| 接线中枢行数 | contracts.ts＋modules.ts＋entities.ts 三文件行数之和 | `wc -l` 相加 |
| 包块尺寸 | 内容包单个 block 行数 | `wc -l` |
| 跨层跳数 | 读懂一步要进几个目录 | 数树涉及的目录数 |

铁律：**这五个数字只做温度计，不做 thermostat**。涨了就在评审里问一句为什么，不许写成测试拦人——一旦进测试，它就从"优雅标准"退化成"正确性门"，这正是本标准要避免的。

## 五、过程：三个时机

1. **开工前画树**：要拆哪一步，先画它今天的阅读树（基线）。
2. **完工后比树**：树变薄还是变厚，差值就是"更好维护"的证据。
3. **评审时问树**：每个包验收加一问——单步三处总行数降没降，引用行少没少。

## 六、新人阅读顺序（通用）

1. 看产物（dist 某步 md，知道长什么样）。
2. 看装配（steps/index 顺序＋contracts 接线，知道谁跟谁）。
3. 看单步（steps/某步 reads，顺着引用读内容域与 assets，知道做法与声明）。
4. 看包（附录对应的 blocks，知道通用形状）。

## 七、与测试的边界

| | 测试（`npm test`） | 本标准 |
|---|---|---|
| 管什么 | 对错（行为、漂移、产物完整） | 优雅（负担、层次、可读） |
| 怎么执行 | 机器跑，红即停 | 人读数，评审问 |
| 谁维护 | 随代码改 | 随结构改（见 §八） |

## 八、维护

- 每新增一个包，给它那一步补一张阅读树（放 `docs/reading-trees/`）。
- 五数基线只增不改口径；数字变了就更新样板里的"今日数"。
- 本文件本身的修改须经作者确认（它是标准，不是记录）。
